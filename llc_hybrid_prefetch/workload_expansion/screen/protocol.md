# Discovery screen protocol

Freeze the following before opening new native results. Use each discovery trace in the intake registry and keep its held-out groups unopened. Each primary arm starts at input instruction 1, warms the first 100,000 instructions, retires the next 250,000 and retains a 256-record input guard. Scheduling does not depend on trace MPKI, IPC or history support. The separate replication panel can use the exact runner and a different registered interval. Use the unmodified two-core Pythia v1.3 study build, one active core in physical page slot zero, one shared memory channel, 4 MiB shared LLC, 64-byte lines and 4 KiB pages. Retain private caches and the same OOO pipeline. Address assignment registers code, store and load pages in input order. Skipping an interval registers its pages without executing those instructions.

Run all relevant prefetchers off or one standalone demand-ingress LLC policy (native Stride, 256-entry previous-delta with native fallback, degree-one SPP port). Use the same physical issuer, one candidate maximum per trigger, original same-page and duplicate checks, open budget and zero added lookup latency. Predictor state observes warmup before measured issuing. Compare actual accepted requests, service and traffic along with fixed-work IPC and cycles. Deduplicate retirement-head cycles in native counters. These are conditional single-active-core results on bounded windows, with no claim about publisher-weighted application speedup.

Check the input ABI, register, branch and memory fields, source operand identity for **every** measured load against native CORE/trace records, per-arm page mappings and every physical LLC ingress. Log support, positive and negative outcomes, including converted, ordinary, remaining, late and upstream outcomes. No trace or policy is removed for low activity or weak predictability.
