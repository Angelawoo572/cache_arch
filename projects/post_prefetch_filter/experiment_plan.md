# Experiment Plan

This plan is written as the story of the experiment: what goes in, what comes out, what is held fixed, what changes, and how to interpret the result.

## 1. Research question

We are not asking a model to predict arbitrary next addresses.

We are asking:

```text
Given a candidate already generated by SPP,
should a small hardware-friendly controller admit it or suppress it?
```

The first action space is binary:

```text
0 = suppress
1 = admit
```

The larger goal is to understand which signals are useful for this decision on different workloads.

## 2. Data flow

```text
ChampSim + SPP
  -> candidate event log
  -> one-row-per-candidate table
  -> offline feature sweep notebook
  -> selected policy
  -> future ChampSim replay with filter
  -> IPC / hit-rate / miss-rate / MPKI evaluation
```

Current candidate table:

```text
projects/post_prefetch_filter/data/generated/spp_candidate_log.csv.xz
```

Current candidate scope:

```text
CANDIDATE_SCOPE = spp_l2_issue
condition       = spp_fill_l2 == 1 or spp_confidence >= 90
```

This means the first experiment focuses on candidates that SPP itself considers strong enough for L2 admission.

## 3. Baseline simulator metrics

Before training or filtering, record SPP baseline behavior for each workload.

Metrics:

```text
trace
IPC
L1D/L2C/LLC access, hit, miss
L1D/L2C/LLC hit rate
L1D/L2C/LLC miss rate
L1D/L2C/LLC MPKI
prefetch issued/useful/useless/accuracy
```

Interpretation:

```text
IPC
  latency/performance outcome

hit rate / miss rate / MPKI
  cache effectiveness and lower-level pressure

prefetch accuracy
  useful prefetches / issued prefetches

coverage
  how many future misses were removed by useful prefetches, when available
```

These are evaluation metrics, not online input features. The filter cannot use final IPC or final hit rate from the same run.

## 4. Candidate logger

For each candidate, log candidate-time state:

```text
trigger_pc
trigger_addr
candidate_addr
candidate_delta
SPP confidence
SPP fill_l2 decision
cache_hit_state at generation time
mshr_occupancy
mshr_size
pq_occupancy
pq_size
bandwidth bucket if available
set pressure if available
```

Then attach delayed outcome labels:

```text
outcome_useful
outcome_late
outcome_evicted_unused
outcome_duplicate
```

The first version has useful/duplicate more reliably than timeliness/pollution. Timeliness and pollution should be improved later.

## 5. Notebook feature sweep

The notebook is an offline controlled experiment. It helps decide which feature combination deserves a real ChampSim replay.

Hold fixed:

```text
workload
candidate scope
train/eval split
reward definition
model family
```

Change one feature group at a time:

```text
F0: candidate identity only
    pc_bucket, delta_bucket, confidence_bucket

F1: add resource pressure
    F0 + mshr_bucket + pq_bucket

F2: add online usefulness memory
    F1 + recent_spp_accuracy + recent_pc_accuracy + recent_delta_accuracy

F3: add bandwidth pressure
    F2 + bandwidth_bucket

F4: add cache context
    F3 + cache_hit + set_pressure
```

For every feature set, record:

```text
issued_ratio
accuracy
useful_kept_ratio
bad_suppressed_ratio
estimated_reward
num_states
```

How to read the table:

```text
accuracy improves but useful_kept_ratio drops
  -> filter may be too aggressive

issued_ratio decreases while useful_kept_ratio stays high
  -> promising traffic reduction

F1 changes the result only when MSHR/PQ pressure exists
  -> resource-aware filtering is workload dependent

F3 changes the result only after real bandwidth_bucket exists
  -> placeholder bandwidth cannot support a bandwidth claim
```

## 6. Simulator replay plan

After the notebook selects promising policies, replay them inside ChampSim.

For each workload:

```text
no prefetch
SPP baseline
SPP + filter F0
SPP + filter F1
SPP + best notebook policy
```

Record deltas relative to SPP baseline:

```text
delta IPC
delta L1D/L2C/LLC hit rate
delta L1D/L2C/LLC miss rate
delta MPKI
delta prefetch issued
delta prefetch useful
delta prefetch useless
delta prefetch accuracy
delta useful coverage
delta MSHR/PQ pressure
```

This is where we answer:

```text
Does the filter improve hit rate or reduce miss rate?
Does it preserve or improve IPC?
Does it reduce useless prefetch traffic?
Does the answer depend on workload?
```

## 7. Workload interpretation template

For each workload, write the result in this format:

```text
Workload:
  trace name

Baseline behavior:
  IPC, hit/miss rates, MPKI, SPP accuracy

Candidate behavior:
  useful rate, issued ratio, MSHR avg/max, cache-hit context

Feature result:
  which F-set changed the policy, which did not

Interpretation:
  TRUST_SPP / RESOURCE_GATE / COVERAGE_PROTECT / DUPLICATE_CLEANUP

Next action:
  replay selected policy or collect missing feature
```

Expected workload roles:

```text
602.gcc
  sanity case: SPP already strong, low MSHR pressure

605.mcf
  resource-pressure case: MSHR/PQ features should be more meaningful

619.lbm
  streaming/coverage case: filter must avoid hurting coverage
```

## 8. Creative design hypothesis

The likely architecture is not one universal aggressive filter. It is a behavior-class controller:

```text
TRUST_SPP
  high SPP usefulness, low pressure
  -> admit most candidates

RESOURCE_GATE
  high MSHR/PQ/bandwidth pressure
  -> suppress candidates with low utility under pressure

COVERAGE_PROTECT
  streaming or high-coverage phase
  -> avoid suppressing too much

DUPLICATE_CLEANUP
  repeated candidates
  -> small recent-exact filter removes redundant traffic
```

The experiment is useful because it tells us which behavior class appears in which workload.

## 9. Stop/go criteria

Continue if at least one workload shows:

```text
same or higher IPC
same or lower miss rate / MPKI
less useless prefetch traffic
no major useful coverage loss
```

Strong result:

```text
higher IPC and lower useless traffic on a memory-pressure workload
```

Acceptable project result:

```text
same IPC with lower traffic and clearer workload-dependent control logic
```
